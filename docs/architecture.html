Identity & access for AI agents

AgentAuthZ: a small model that authorizes what AI agents do

Every time an agent calls a tool on a user's behalf, AgentAuthZ decides ALLOW, STEP_UP or DENY, shows the checks behind the decision, and cites the policy it used. It is a fine-tuned Llama-3.2-3B served locally by Ollama, grounded in org policy with RAG, and backed by a deterministic guard.

1. One tool call, end to end

Follow a single agent request from left to right. The fine-tuned model reads the event, the vector store supplies current policy, and the guard enforces a floor before anything runs.

2. How the model was built

Rule-labeled events teach the model a decision procedure. The labels come from a transparent rule engine, so every training target is reproducible.

3. What RAG changes: the revoked-agent case

Same event, same model. The only difference is one retrieved chunk from the agent registry.

  1. Show the gap. Ask the base model about Q2: an agent releasing a payment with no act claim and an escalated scope. It answers ALLOW. 
    ollama run llama3.2:3b
  2. Show the fine-tuned analyst. Same event. The checks flag act_claim: "missing". The 4-bit model's raw answer is STEP_UP, and the guard in rag_pipeline.py escalates it to DENY. 
    ollama run agentauthz
  3. Show RAG. In the LangFlow Playground, paste R1 from eval/questions.md. The answer is DENY and cites acme_agent_registry.md.
